# 缓存与请求合并

`expiredTime` 同时控制请求合并与结果缓存，不是 Axios 的网络超时。网络超时请使用 `config.timeout`。

## 三种模式

| `expiredTime` | 等待中的相同请求 | 已完成结果 |
| --- | --- | --- |
| `< 0`，例如 `-1` | 分别发送 | 不缓存 |
| `0`（默认） | 合并并共享结果 | 分发窗口结束后删除 |
| `> 0`，例如 `2000` | 合并并共享结果 | 缓存到 TTL 结束 |

```ts
await api.request({ url: '/users' }, -1)   // 独立执行
await api.request({ url: '/users' })       // 仅合并
await api.request({ url: '/users' }, 2000) // 合并并缓存
```

## 请求如何匹配

合并后的 Axios 配置生成缓存键；实例模式也考虑 `instance.defaults`。URL、方法、请求参数、请求体和请求头的差异会影响匹配。

当前实现按内容处理普通对象、URLSearchParams、FormData 文本字段、二进制数据和 AxiosHeaders。函数、取消控制器、上传文件及任意自定义对象按身份保守区分。

普通对象的属性顺序不影响键。不同上传文件对象即使内容相同，也可能不合并。自定义对象内部状态和拦截器闭包里的外部状态无法完整推断，应使用独立请求或在配置中显式表达变化。

## 首次调用决定策略

同一个请求组使用第一个调用者的 TTL、重试次数和延迟。后续调用不会更新组内策略。

```ts
const first = api.request({ url: '/users' }, 2000, 2, 300)
const second = api.request({ url: '/users' }, 0, 0)
await Promise.all([first, second])
// 两者共用 first 的策略
```

## 成功与失败都可缓存

正 TTL 同样缓存普通错误。例如 500 响应失败后，有效期内的调用会得到同一个拒绝结果，而不会马上访问服务器。取消错误不长期缓存。

返回值使用原始对象引用。修改 `response.data` 也可能改变其他调用者看到的数据；需要独立数据时，由应用自行复制。

## TTL 与分发时序

为兼容旧项目，首个调用者返回后，结果在下一次定时器任务中分发给等待者。TTL 从分发时开始计算。TTL 为 0 时，同一分发窗口内的调用仍可能共享结果。

每次命中都检查 TTL。过期条目随后续启用合并的请求定期清理；空闲时不会自动清空，当前也没有容量上限或公开的清空缓存方法。

::: warning 写操作
POST 等方法也会参与合并。若每次提交都必须独立执行，请设置 `expiredTime = -1`。客户端合并不能代替服务端幂等机制。
:::
